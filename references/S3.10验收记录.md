# S3.10 验收记录 · 索引自动化、库级单次检索与判分重建 · 0.13.0

日期：2026-10-23（Asia/Shanghai）。分支：`codex/retrieval-budget-en-rerank`。应用版本 0.13.0，API `/health` 的 `version=0.13.0`、`slice=S3.10`。本轮没有调用任何外部模型、联网搜索或付费服务；用户论文与原始 PDF 未被改写，`data/` 未纳入 Git。

## 1. 用户规格与唯一执行选择

按用户 23 行规格逐条实现（解析后自动建索引、稀疏预处理落盘、进程内缓存、单库检索、全局 Top 60、删除每篇保底、判分改为“能否完整回答”、定向补检 1 次、账本累积、3 次调用上限、页面与进度文案）。

用户留待确定的一项——“建索引是后台排队（解析立即返回、页面显示‘索引中’）吗”——本切片选择**后台排队**：

- 解析本身已经可达数分钟，再串行叠加 1–2 分钟编码会让上传请求逼近 UI/HTTP 超时；
- 目标明确要求“解析失败与索引失败分开记录，可单独重试”，后台队列天然把两者分成两个状态域；
- 页面已有 `GET /documents/{id}/index` 与 `/agent/scope` 的状态入口，只需增加 `building/failed` 文案。

代价与对策：进程内队列不跨重启，用 `retrieval/pending.json` 标记 + 启动 `resume_pending()` 补齐；不引入持久化任务系统。`POST /documents/{id}/index` 仍是**同步**的手动建立／重试入口（用户要求保留）。

## 2. 变更

| 方面 | 变更 |
| --- | --- |
| 解析→索引 | `IngestionService` 新增 `on_parsed` 回调；`IndexService.queue_build` 单线程后台构建 `dense.faiss` + `bm25.json`，`pending.json` 标记中断可恢复；`resume_pending()` 在启动时重建中断与非就绪的论文 |
| 稀疏预处理 | 新增 `app/retrieval/bm25.py`：每块 tf/长度、每篇 df、倒排表、`length_sum`、自报字节数；查询期只对问题分词，`BM25Library` 合并选中集合的 df 算 IDF（`log(1+(N-df+0.5)/(df+0.5))`）后查倒排 |
| 索引完整性 | `IndexManifest` 增加 `bm25_sha256`；`current()` 同时校验两个文件；指纹仍匹配、仅缺稀疏文件的旧索引由 `_backfill_sparse` 直接补 `bm25.json`，不重新编码向量（切分或模型变过则正常重建） |
| 失败记录 | 新增 `document_index_failures`（schema v6，只增表）；`status()` 区分 `building/ready/failed/stale/missing` 并回传错误码与原因 |
| 缓存 | 新增 `app/retrieval/cache.py`：键 `(document_id, fingerprint)`，`get/peek/retain/discard`，30 分钟空闲 TTL、300 MB、8 组 LRU；命中缓存时不再重算文件哈希 |
| 检索 | `app/retrieval/search.py` 重写为 `library_candidates`（稠密全局 Top 60 + BM25 全局 Top 60 → `fuse` RRF → 60）；删除 `rank_candidates` 的每篇深度、`retrieval_depth` 与每篇保底 2 条 |
| 判分 | `ModelAnswer` 增加 `sufficient/covered/missing/next_query`；`GRADE_PROMPT` 判“本轮文档能否完整回答本轮问题”；`missing_points` 丢弃问题中不存在的数字与表/图号 |
| 轮次 | `CorrectiveAgent` 图：`route → translate → retrieve → rerank → grade → targeted_retrieve → rerank → grade → generate`（`web_search` 仅在无本地证据时兜底）；`ledger` 跨轮按 `(document_id, id)` 去重，生成前重编号 E1…En 并按字节裁剪 |
| 调用预算 | `call(..., counted=False)` 只用于英译；`agent_max_calls` 7→3；`TokenUsage` 仍累计英译 token，只是不计次数 |
| 配置 | 删除 `per_paper_candidates`；新增 `auto_index`、`index_cache_mb/entries/ttl`；`.env.example` 同步 |
| 页面 | Agent 页与单篇问答页显示“索引中／索引失败可重试／待建立”，保留手动入口；进度标签改为“判分：本轮文档能否完整回答”“定向补检（第 2 轮）”；`/agent/status` 暴露 `max_targeted_retrievals`、`index_cache`，移除 `max_rewrites` |
| 评估 | 新增 `evaluation/replay_retrieval.py`；`collect_answers.py` / `collect_pilot.py` 改走库级检索，并记录 `sufficient/covered/missing/ledger` |

依赖未升级、未新增（`rank-bm25` 仍安装但查询路径不再使用）；`CHUNK_VERSION` 仍为 v4，切分文本未变。

## 4. 免费离线重放（不调用 LLM／联网）

目的：在付费复测前先看“新检索是否把金标准证据找回来”。

- 运行数据：把历史五篇真实论文 runtime（`output/evaluation/expanded-v0.3-rag-0.11.2/runtime`）复制到 `output/evaluation/replay-v0.13/runtime`，不修改原评估产物与用户 `data/`。
- 题目：`evaluation/datasets/v0.2/rag_questions.jsonl` 中 `ADD-` 前缀 25 题（与 S3.9 同批）。
- 模型：本地 BGE-M3 编码 + 新 `bm25.json` + 本机 Cross-Encoder 精排；**未调用任何 LLM、Tavily 或付费接口**。
- 命令：
  ```
  uv run python -m evaluation.replay_retrieval \
    --runtime output/evaluation/replay-v0.13/runtime \
    --questions evaluation/datasets/v0.2/rag_questions.jsonl \
    --prefix ADD- --out output/evaluation/replay-v0.13/coverage.json
  ```

结果（22 道有直接金标准的可回答题；3 道应拒答题无金标准，单列不计分）：

| 指标 | 结果 |
| --- | --- |
| 金标准**全部**进入融合 Top 60 | **22/22** |
| 金标准**至少一条**进入融合 Top 60 | **22/22** |
| 金标准全部进入原问句精排 Top 12 | 15/22 |
| 金标准至少一条进入原问句精排 Top 12 | 17/22 |
| 总耗时 | 461.4 秒（本地 CPU） |

5 道“池内有、原问句 Top 12 无”的题：`ADD-MOD-004`（池 rank 2）、`ADD-MOD-005`（12）、`ADD-CMIR-002`（17）、`ADD-WIS-004`（8）、`ADD-WIS-005`（1）。25 题全部为中文问句；本重放没有英译（英译需要 LLM 调用），而生产路径会先英译再精排，故 Top 12 数字对中文题偏悲观。S3.8 的冻结候选重放显示同一批中文题换英文精排后 Top 12 至少一条为 22/22。

结论：新单库检索已不再是召回瓶颈（60 条池 22/22 全覆盖）；剩余变量是精排语言与判分／生成，无法用免费重放判断。逐题数据见 `output/evaluation/replay-v0.13/coverage.json`（运行产物，不入 Git）。

## 5. 未运行与限制

- **未**重跑 25 题端到端付费生成（S3.9 为 0.12.0、22/25）。按协议需用户再次明确授权，且应先看本轮重放结论再决定。
- **未**做真实浏览器页面核对（只做 AppTest 页面断言）。本机 API/UI 未重启验证 0.13.0；本机 `data/` 现有 4 篇索引建于 `CHUNK_VERSION v4` 之前（实测指纹不匹配、dense 哈希匹配），启动后会在后台**重新编码一次**（约 1–2 分钟/篇，共约 4 篇），不是只补 `bm25.json`。补齐路径只在指纹仍匹配、仅缺稀疏文件时生效。
- 离线重放使用页面+文本重叠匹配金标准（`evidence_text` 子串或 ≥60% 词重叠），不是逐字金标准切片；`ADD-CMIR-005`、`ADD-MAM-005`、`ADD-PS-005` 三道应拒答题无 relevance=2 金标准，未计入覆盖分母。
- 进程内缓存与后台队列都是单进程假设；多 worker 部署时每个进程各自缓存、各自建索引，本轮不做分布式协调。
- `missing` 的服务端护栏比“对照问题与证据”更严：缺口里出现问题之外的数字或表号即丢弃，宁可少列缺口也不猜。
