## 1. 用户规格与唯一执行选择

按用户 23 行规格逐条实现（解析后自动建索引、稀疏预处理落盘、进程内缓存、单库检索、全局 Top 60、删除每篇保底、判分改为“能否完整回答”、定向补检 1 次、账本累积、3 次调用上限、页面与进度文案）。

用户留待确定的一项——“建索引是后台排队（解析立即返回、页面显示‘索引中’）吗”——本切片选择**后台排队**：

- 解析本身已经可达数分钟，再串行叠加 1–2 分钟编码会让上传请求逼近 UI/HTTP 超时；
- 目标明确要求“解析失败与索引失败分开记录，可单独重试”，后台队列天然把两者分成两个状态域；
- 页面已有 `GET /documents/{id}/index` 与 `/agent/scope` 的状态入口，只需增加 `building/failed` 文案。

代价与对策：进程内队列不跨重启，用 `retrieval/pending.json` 标记 + 启动 `resume_pending()` 补齐；不引入持久化任务系统。`POST /documents/{id}/index` 仍是**同步**的手动建立／重试入口（用户要求保留）。

### 4.1 精排保留条数 12→10（0.13.1，用户要求省 token）

方法：`evaluation/measure_top_n.py` 从 S3.9 记录中恢复每题**实际使用的英文精排问句**（不调用 LLM），对同一 60 条融合池重排，统计每个 k 的金标准覆盖与判分证据 JSON 字节。命令：

```
uv run python -m evaluation.measure_top_n \
  --runtime output/evaluation/replay-v0.13/runtime \
  --questions evaluation/datasets/v0.2/rag_questions.jsonl \
  --translations output/evaluation/expanded-v0.3-rag-0.12.0/agent_outputs.json \
  --out output/evaluation/replay-v0.13/top_n_sweep.json
```

| k | 金标准至少一条 | 金标准全部 | 证据字节均值 | 相对 12 条 |
| --- | --- | --- | --- | --- |
| 4 | 19/22 | 17/22 | 1,882 | −67.4% |
| 6 | 20/22 | 18/22 | 2,826 | −51.1% |
| 8 | 21/22 | 20/22 | 3,838 | −33.6% |
| **10（新默认）** | **22/22** | **22/22** | **4,771** | **−17.5%** |
| 12（旧默认） | 22/22 | 22/22 | 5,782 | — |

解释与限制：

- 条数只决定“多少条候选进入判分、并可能进入账本”，不影响 60 条融合池的召回；每次判分都会带上这些原文，不足时还有第 2 次判分，所以它是每次提问的主要证据 token 来源。
- k=10 是本批 25 题里“不丢召回”的最小值；k=8 丢 `ADD-PS-001`（其金标准在 rank 10）。样本只有 22 道有金标准的题，不能保证未来题目 rank 11–12 不需要，所以 12 仍保留小幅安全边际，可在 `.env` 用 `RESEARCH_RERANK_TOP_N=12` 恢复。
- 生成阶段的账本另有 `context_bytes`（默认 24,000 字节）硬上限，减少 k 也会让账本更早停止增长，但节省的主要是判分。
- 未用真实 LLM 验证“10 条是否改变判分结论”，因此本轮只声明检索覆盖与证据字节，不声明回答成功率变化。
- 0.13.1 复跑：`pytest` **246 passed / 4 skipped**（新增 `tests/test_settings_defaults.py` 钉住 `candidates=60`、`rerank_top_n=10`、`agent_max_calls=3` 与自动建索引默认开启）、ruff、格式、mypy（96 文件）、compileall、`uv lock --check`、`uv pip check` 通过。

### 4.2 图表引用在生成前组装（0.13.2／0.13.3）

用户提出“图表的 caption 最好跟引用它的段落在一起，而不是单独一个 chunk”，并明确两条修正：**caption 一定和图表绑定**（段落被选中而对应的表/图没被选中时不附加 caption）；组装时**不要控制字节**。

核对现状（五篇真实论文）：

| 索引单元 | 生成方式 | 页码/坐标 | 与引用位置的关系 |
| --- | --- | --- | --- |
| 正文片段 | 每个 block 按 700 字、100 重叠切 | 段落自己的页/框 | 段落自身 |
| 表格行 | 每张表逐行一个 chunk（>700 再拆） | 表格页 + 表框 | 前缀只带引用段落的**章节路径**，不带引用句 |
| 图注 | 图注 block 当普通正文 chunk（无独立图片单元） | 图注页 | 无 |
| 图内文字 | 被 `figure_region_text` 排除 | 不索引 | — |

- 一篇 24 页论文：12 张表 → 61 个行 chunk（约 17%）；每行前缀重复 caption 前 300 字；21 个 caption block 又被当正文索引（命中 23 个 chunk），表注实际存两份。
- 引用关系统计：**表格 49/54、图 27/45** 能在正文找到带编号的引用段；8 张表被引用 2–4 次；3 张表、11 张图连编号都没有。所以“有图/表就一定有引用段”不成立，组装必须允许降级。
- caption 长度：54 张表中 5 张超过 300 字（最长 486），行前缀会截断这部分。
- 顺带确认一个文本 bug：行 chunk 前缀是 `Table 1: Table 1: …`（label 与 caption 都带表号），本切片刻意**没有**改它，避免触发重建；留待下一次切分修订一起处理。

实现（不重建索引）：

- 新增 `app/services/evidence_context.py`：`attach_references(evidence, documents, manifests)`；
- `CorrectiveAgent.generate` 通过 `enrich` 回调在重编号前组装一次；`AgentAnswerService` 提供 documents/manifests；组装异常时回退原始账本，不让一轮问答因组装失败而中断；
- 规则：表格行 / 图注被选中 → 用解析阶段的 `mention_block_ids` 找到引用段落的 chunk，**整段**并入（0.13.3 起不再截断）；该 chunk 也在账本中时整段合并并删除重复项，否则保留原项并附整段；同一段落只附加一次；caption 超出 300 字的部分以“表注（续）”补回、**每表一次**；其余证据（包括被选中但没有图表的段落）**原样不动**；
- 判分仍看原始行（提示词不变大）；引用页码仍是表/图页，正文里写明引用段页码；
- **不做字节截断**：唯一剩下的限制是单轮 `context_bytes`（24,000 字节）预算，超限时按整条证据取舍，不会把一段话切成半句。

组装后的真实体积（五篇、407 个表格行证据项，`tmp` 诊断脚本量测，不入 Git）：

| 指标 | 值 |
| --- | --- |
| 平均 | 479 字节 |
| p50 / p95 | 431 / 1,012 字节 |
| 最大 | 1,408 字节 |
| > 1 KB | 23 条 |
| > 1.5 KB | 0 条 |

测试：`tests/test_evidence_context.py` 14 项，覆盖合并、去重、段落单独出现时不变、无引用段不变、长段落不截断、长 caption 保留续文且每表一次、短 caption 不追加、多行只附加一次、未知文档不动、端到端进入生成提示。

限制：引用段依赖解析期的表号/图号正则匹配，匹配不到就降级为不附加；图内像素数值仍不可检索（需裁图 + 多模态模型，明确不做）；本轮未跑付费端到端，不声明回答成功率变化。

复跑：0.13.2 时 `pytest` **256 passed / 4 skipped**；0.13.3（去掉字节上限）后 **260 passed / 4 skipped**；ruff、格式、mypy（97 文件）、compileall、`uv lock --check`、`uv pip check` 均通过。

- 进程内缓存与后台队列都是单进程假设；多 worker 部署时每个进程各自缓存、各自建索引，本轮不做分布式协调。
- `missing` 的服务端护栏比“对照问题与证据”更严：缺口里出现问题之外的数字或表号即丢弃，宁可少列缺口也不猜。

## 6. 下一步建议

1. 是否付费重放 25 题由用户决定：若目标是验证“判分 + 定向补检 + 账本”对回答成功率的影响，需要 3 次/题的模型调用（中文题多 1 次英译）。
