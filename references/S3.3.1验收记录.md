# S3.3.1 保存密钥后重启断连修复

日期：2026-10-22（Asia/Shanghai）；应用 0.7.1。根目录当前无 `.git`，开始和交付前检查均返回非 Git 仓库；无法形成原分支提交、报告哈希或检查 staged diff，未初始化替代历史、未推送。

## 故障复现与证据

用户保存 API 密钥后，先运行停止 cmd、关闭旧页面，再运行启动 cmd，新页面显示“无法连接服务或响应无效”。没有将其归因于旧页面或要求重输 Key。

- 默认端口 API 与 UI 都在监听，API /health 和 /documents 为 200，model_configured=True；说明密钥已被本机后端读取，不代表供应商生成已验证。
- 实际浏览器设置页仍报同一连接错误，API 访问日志没有对应页面请求。
- 通过短暂的无值传输诊断确认实际 UI 进程访问 /health 收到 **status=502、json=False、proxy_present=False、loopback_bypass_present=False**。仅记录状态 / 类型 / 布尔值，不记录凭据、代理地址或响应正文；诊断代码已从最终文件移除。
- 同机子进程移除 HTTP_PROXY / HTTPS_PROXY / ALL_PROXY / NO_PROXY 环境变量后复现：HTTPX trust_env=True 返回 502 非 JSON，trust_env=False 返回 200 JSON。Windows 系统代理在无代理环境变量时仍影响了该请求；工具终端环境带 NO_PROXY，因此最初终端健康检查不能代表 UI 传输路径。
- 另以无效代理 http://127.0.0.1:1 且无回环绕过规则复现旧客户端失败；修订后的同一 api('GET', '/health') 返回 ok。没有调用外部模型。

## 修改范围

- client 按 API_BASE 的 hostname 判定回环地址：127.0.0.1 / localhost / ::1 使用 trust_env=False，覆盖普通 API 和原页 / 图片请求。显式非回环地址仍保留原环境行为；未修改供应商请求、全局代理或系统设置。
- ConnectionFailure 区分本机传输 / 无效响应；main 提供手动“重新连接本机服务”，不自动重试上传 / 问答 / 其他 POST，不回显错误响应内容。已有正常业务错误仍按原流程呈现。
- 应用 / health / 锁根版本更新为 0.7.1 / S3.3.1；依赖及 schema 不变。未读取或修改实际 Key 值、`.env`、用户 PDF、解析记录、人工字段或索引。
- 开始前的 client.py / main.py 快照在忽略目录 output/connection-071-before；已用 git diff --no-index 审查这两个文件差异。临时诊断无残留。
